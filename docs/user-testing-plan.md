# 真实用户试用方案

> **为什么这份文档最重要**：项目里所有数字都是自评。12/14、11/44、18 条判据——全是你和 AI 一起判的。
> 面试官一定会问"有人用过吗，他们说什么"。没有这一项，前面所有工作都只能算"自我感觉良好"。
>
> 目标：**找 3–5 位数字人文/中文系同学，跑一遍，录下他们的原话。**
> 不需要证明产品好，**需要的是真实的反应**——包括"这说的什么玩意"。

---

## 一、测什么（只测三件事）

不要让他们"随便玩玩"。给明确任务，才能得到可比的结果。

| # | 任务 | 看什么 |
|---|---|---|
| 1 | 打开内置案例《孔乙己》，点文学诊断 | **能不能看懂结果在说什么** |
| 2 | 挑一条诊断，点开它的证据 | **相不相信这个判断** |
| 3 | 问："如果这条说错了，你怎么告诉它？" | **有没有纠错路径（现在的答案是：没有，这是已知缺陷）** |

---

## 二、怎么问（关键：不要引导）

### 通用问题（每个人问）

1. 你刚才看到的第一屏，你觉得这个工具是干什么的？
2. 有没有哪条诊断让你觉得"说得对"？哪一条？
3. 有没有哪条让你觉得"这不对"或者"这不废话"？哪一条？
4. 你怎么判断它说得对不对？靠什么？
5. 如果让你在作业里用它，你会用吗？为什么？

### 追问句式（对方给出模糊回答时）

| 他们说 | 你要追问 |
|---|---|
| "还行" | 哪一条还行？能指给我看吗？ |
| "有点意思" | 有意思在哪？是功能有意思，还是结论有意思？ |
| "不太懂" | 是这个词不懂，还是这个判断你不认同？ |
| "挺好的" | 如果只能留一条诊断，你留哪条？ |

**不要问**："你觉得这个是不是很厉害？"——这是引导，会把答案带偏。

---

## 三、记录什么（原话比总结值钱）

每人一份记录，格式如下：

```markdown
## 被试 N（专业/年级）

**任务 1：能否看懂**
- 原话：
- 卡在哪：

**任务 2：是否相信**
- 他说"说得对"的诊断：（截图或引用）
- 他说"不对"的诊断：（截图或引用）
- 他判断依据：

**任务 3：纠错路径**
- 他的第一反应：
- 他期望怎么改：

**最有价值的一句原话**：
```

**最重要的一项**：**"他说不对的那条诊断"**。

因为这是你唯一能验证"18 条判据到底有没有用"的地方。如果他说不对，而你觉得对——那要么判据不够严，要么你俩对"好"的定义不同，**两种都值得写进面试答案**。

## 四、结果怎么用（写进 README）

不管结果好坏，都要写。**坏结果反而更有说服力**——因为它证明你真去问了，而不是自说自话。

### 如果多数人说"看不懂"

→ 这是**产品问题不是技术问题**。说明诊断结果缺少"人话解释"。
→ 面试答案："用户测试发现 4/5 的人看不懂术语层，所以下一步是做一层白话转译，而不是加更多判据。"

### 如果多数人说"说得对但没用"

→ 说明**价值主张有问题**：诊断准确但不解决他的实际问题。
→ 面试答案："调研发现学生不缺'哪里不好'的判断，缺的是'那怎么改'。所以下一版加了修改建议。"

### 如果多数人说"这不废话吗"

→ **最严重**，说明判据还是太粗。
→ 面试答案："这直接印证了 11/44 的命中率数据——诊断还停留在表面。接下来的判据注入就是解决这个。"

## 五、去哪找人（按可行性排序）

| 渠道 | 成本 | 备注 |
|---|---|---|
| 同班/同专业同学 | 最低 | 直接约，10 分钟就够 |
| 专业课老师 | 中 | 老师视角更严，能看到你没看到的 |
| 学校写作社团 | 中 | 真实使用场景 |
| 线上（小红书/知乎） | 高但样本好 | 陌生人不留情面，反馈更真 |

**建议先找 3 个同学 + 1 位老师。** 老师那一份最有价值——他可能一句话点破你的判据哪里不对。
