## 3.1 ★ 六次 0/14 的真根因（2026-11-18）

**不是模型差，是判定标准错了。**

`domainAnalysis` 里模型用领域原生词，每个样本都不一样：

```
relationshipChanges: {from,to} {change,pair} {cause,from,to} {change,characters}
                     {after,before,pair} {change,from,to} {from,reason,to}   ← 7 种
turningPoints:       {point} {description} {event,significance} {event} {name,description}
setups / payoffs:    各 3–5 种
```

校验要求 `{label, description}`，模型给 `{from, to}`。**补别名永远追不上。**

**改法**：判定标准从「必须叫某个字段名」改成「**有内容 + 有证据**」。

**判据没放松**——引文仍须逐字在原文、`evidenceIds` 仍须指向真实证据、六项指标仍须齐全。松掉的只是**字段命名**，那是实现细节不是产品承诺。

**工具**：`scripts/offline-validate.py` —— 用 raw 离线复算，不花钱不限次数。**以后任何一轮失败先跑它。**

## 4.1 AC19 怎么验（用成熟方案，不靠碰运气）

**不重复花钱重跑三轮。** 用已有的 raw + 归一化层做**离线稳定性模拟**：

行业里衡量 LLM 输出稳定性的标准做法是 **pass@k / 多次采样的通过率分布**（不是"同一个输入跑三次看运气"）。
本项目的等价做法：

| 步骤 | 做什么 | 成本 |
|---|---|---|
| 1 | 同一批 14 条样本跑 **3 轮 live**，各自落 raw | 约 2.1 元 |
| 2 | 三轮都用 `offline-replay.test.ts` 复算通过数 | 免费 |
| 3 | 三轮通过数极差 ≤ 2 即达标 | — |

**中途可先做**：拿现有两批（11-18 的 14 份 + 11-19 的 14 份）当两轮，先算一次极差。若已是 12–13，说明稳定性在可接受区间。

**为什么不用"同一输入重试到成功"**：那会把失败概率乘方，看起来稳，实际掩盖了根因。本项目已把失败率从 100% 降到 ~14%，先看分布再说。

## 7. 方法论教训（写下来防止重犯）

**前四批空转的根本原因不是模型差，是我一直用 warnings 逐层猜。**

`warnings` 只能告诉你"哪个字段非法"，告诉不了你"值被放进了哪个字段"。正确做法是：

1. **raw 响应落盘**（第四批已做）
2. **离线校验器一次扫出全部失败点**（已建）
3. **一次修完，不要分层修**

第四批之后用这个方法，**十分钟定位，零 API 成本**。前四批每次花 0.7 元、等十分钟、只修一层。

**这条经验适用于所有后续 Sprint。**
