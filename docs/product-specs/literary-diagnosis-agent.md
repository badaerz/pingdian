# 产品规格：防幻觉文学诊断 Agent

**版本**：0.1（2026-11-17）
**来源**：`故事熔炉_PRD_v2.0_AIPM收敛执行清单.docx` §3.1–3.4 的工程化落地
**状态**：核心模块，占本期 90% 精力

## 1. 一句话

用户提交一段文本，系统给出**可核验的文学诊断**；每条诊断必须同时绑定「原文位置」和「知识库判定依据」，
两者缺一即判定为无证据，**该条单独丢弃并记录丢弃原因**，不影响其余结论。

## 2. 目标用户与场景

| 用户 | 场景 | 成功信号 |
|---|---|---|
| 大学生创作者 | 把自己写的一段贴进来，想知道哪里写得不好、为什么 | 3 条以上诊断能直接落到自己的句子上，且说清了"为什么是问题" |
| 文学/写作教师 | 课堂上演示"文学判断是怎么做出来的" | 能点开任意一条结论，看到它引用的原文和它依据的评判标准 |
| 评委/面试官 | 15 秒内判断这个项目有没有真东西 | 一眼看到"丢弃了 3 条无证据结论"，并看到丢弃原因 |

## 3. 与现状的差距（基线证据见 exec-plans）

| 要求 | 现状 | 差距性质 |
|---|---|---|
| 每条诊断有原文锚定 | 有 `quote` + `exactQuoteExists` 校验 | ✅ 已具备 |
| 每条诊断有知识库依据 | 只有 `evidenceIds` 指向 evidence，且只校验"含 observation"，**不校验是否含 knowledge** | ⚠️ 一半 |
| 无证据逐条丢弃 | **整包 all-or-nothing**（`validation.ts:340`），一条不合格则全部作废 | ❌ 相反 |
| 丢弃原因可展示 | 无 | ❌ 缺 |
| 知识库是"评价维度" | 是按**作品**组织的技法说明，不是按维度组织的判定标准 | ❌ 结构不符 |
| 诊断落在文学维度上 | prompt 未约束维度，实测大量输出退化为**校对意见**（"措辞略生硬"） | ❌ 缺 |

## 4. 功能需求

### F1 逐条裁定（P0，本期必做）

`analysis-v2` 的校验从"整包接受/整包拒绝"改为"逐条裁定"。

**判定规则**（每条诊断独立执行）：

| 条件 | 结果 |
|---|---|
| `quote` 无法在原文逐字定位 | `discarded`，原因 `quote_not_in_source` |
| `evidenceIds` 不含任何 `observation` 证据 | `discarded`，原因 `no_observation_evidence` |
| `evidenceIds` 不含任何 `knowledge` 证据 | `kept`，但标记 `evidenceTier: "observation_only"` |
| `confidence` 超出 0–1 | `discarded`，原因 `invalid_confidence` |
| 以上皆过 | `kept`，`evidenceTier: "anchored"` |

**重要**：`observation_only` **不丢弃**。理由：原创作品没有对应知识条目（GC_012、GC_014 就是这种情况），
要求必须有知识库依据会把整个原创写作场景判死。但它必须在界面上与 `anchored` 视觉区分，
并在指标里单独统计。这是有意的分级，不是妥协。

**整包丢弃只在三种情况下发生**：JSON 不可解析、顶层字段结构不符、`diagnostics` 非数组或为空。
这三种属于"模型没按合同说话"，不是"某条结论没证据"。

### F2 丢弃记录（P0）

`LiteraryAnalysisResult` 增加 `discardedDiagnostics`：

```ts
interface DiscardedDiagnostic {
  id: string;
  reason: "quote_not_in_source" | "no_observation_evidence" | "invalid_confidence" | "invalid_shape";
  attempted: { location?: string; quote?: string; effect?: string; action?: string };
}
```

即使某条诊断整体无效，也要保留它**试图说什么**，否则无法向用户解释"系统替你挡下了什么"。

### F3 四段可解释面板（P0，唯一显著增加前端工作量的模块）

在 `/project/[id]/analysis` 页面，诊断结论下方增加可展开面板。四段各自独立渲染，
**无数据时显示明确空状态文案，不得留白**。

| 段 | 展示内容 | 数据来源 |
|---|---|---|
| 输入段 | 本次被诊断的文本（高亮诊断涉及的范围）、文本字数、`sourceKind`、`contextRevision`、触发时间 | 已有 |
| 检索段 | 召回了哪些知识条目（`retrievalId` + `chunkType` + 内容摘要 + `sourceStatus`）、命中原文的哪些片段、相关度；**一条都没召回时必须明说"本次未召回知识条目"** | `result.retrievalEvidence` |
| 任务段 | Agent 的判断：每条诊断的维度、观察、影响、建议、置信度 | `result.diagnostics` |
| 校验段 | 每条结论的证据状态（`anchored` / `observation_only` / `discarded`）+ 丢弃原因；**被丢弃的单独列出** | `result.diagnostics` + `result.discardedDiagnostics` |

面板的验收话术（这是给评委的一句话）：
> "这段是 AI 看的文本，这段是它查到的依据，这段是它的判断，这段是它自己否掉的东西。"

### F4 维度约束（P0）

prompt 必须把诊断限定在固定维度集合内，并显式排除校对类意见。

固定维度（与 golden set 的 `dimension` 字段一致）：
`伏笔与铺垫`、`视角与叙述者`、`结构与反讽`、`意象与主题`、`节奏控制`、`人物塑造`、`人物弧光`、`对话潜台词`、`感官描写`、`语言控制`、`主题表达`、`道具叙事`、`叙述干预`、`暗示与明写`、`留白与结局`、`情节因果`。

**显式排除**：错别字、用词生硬、标点、语法、方言可读性。
判据：**如果这条意见换成另一段文字也成立，它就不是针对这段文本的诊断。**
（"`'育养'一词稍显生硬`" 对任何含该词的文章都成立 —— 属校对。）

### F5 非目标（本期明确不做）

- 不做自动改写。诊断只说问题在哪、为什么，不改写用户文字。
- 不做打分总评。分数会诱导用户只看数字，掩盖证据。
- 不做跨章节整体诊断。本期限定单段文本，长度 150–3000 字。
- 不接入向量检索。离线关键词检索够用，向量是 P2。

## 5. 验收标准

每条都必须可机器检查或有明确人工步骤。

**F1 逐条裁定**
- [ ] 构造一个 payload：3 条诊断，其中第 2 条 `quote` 不在原文。断言：返回 2 条 `kept` + 1 条 `discarded`（原因 `quote_not_in_source`），而非整包拒绝。
- [ ] 构造一个 payload：某条诊断 `evidenceIds` 只指向 `inference`。断言：该条 `discarded`，原因 `no_observation_evidence`。
- [ ] 构造一个 payload：合法诊断但 `evidenceIds` 不含 knowledge。断言：该条 `kept` 且 `evidenceTier === "observation_only"`。
- [ ] 构造一个 payload：`diagnostics` 缺失。断言：整包回退 demo（这是合同违约，不是单条问题）。
- [ ] 删除 `validation.ts:341` 的"铺垫不足"强制要求，并补一条回归测试断言它不再存在。

**F2 丢弃记录**
- [ ] 上述第一个用例中，`discardedDiagnostics[0].attempted.quote` 等于被拒的原始引文，不是空字符串。

**F3 面板**
- [ ] 打开 `/project/demo/analysis`，四段标题均可见。
- [ ] 在无知识召回的样本上，检索段显示"本次未召回知识条目"，不是空白。
- [ ] 在存在丢弃的样本上，校验段列出被丢弃条目及其原因。
- [ ] 键盘 Tab 可依次到达四段内的所有可交互元素。

**F4 维度约束**
- [ ] 用 GC_001 跑 live，输出中不出现"生硬/直白/冗长/费解/混淆/不搭"等校对词。
- [ ] 每条诊断的维度落在 F4 的 16 个维度集合内。

**整体**
- [ ] `npm run eval --live` 跑全量 14 条，结论准确率与幻觉率写入 `evals/runs/`，与基线对比。
- [ ] `npm run verify` 全绿。

## 6. 已知权衡（面试会被问）

**为什么 `observation_only` 不丢弃？**
因为原创作品没有对应知识条目。要求必须有知识库依据，等于宣布"只有经典作品能被诊断"，
与产品面向创作者的核心场景矛盾。分级标记比一刀切诚实。

**为什么不在校验层强制"必须有一条铺垫不足"？**
那会让校验器变成内容生成器，并且逼模型造不存在的缺陷。
演示需要那一条时，用 prompt 引导 + 证据校验保证。

**知识库重构什么时候做？**
逐条裁定和维度约束是小时级改动，知识库从"按作品"改为"按维度"是周级。
先用小时级的改动把链路跑通并拿到分数，再决定知识库重构的 ROI。
如果维度约束之后准确率仍未显著提升，那才证明瓶颈真的在知识库。
