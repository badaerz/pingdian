# 检索契约 v1.0

**这份文档是给写代码的人看的。**它定义"判据怎么被送进模型"，不定义"模型怎么判"。

| 项目 | 内容 |
|---|---|
| 版本 | v1.0（草案，未实施） |
| 对应知识库 | `判据知识库_v1.0.md`（18 条判据，六维） |
| 对应代码 | `src/lib/ai/retrieval.ts`、`src/lib/ai/tasks.ts`、`src/app/api/ai/route.ts` |
| 状态 | 代码**尚未改动**。本文只定契约，不动实现 |
| 前置事实 | 用户实测：查 `S2`/`P1`/`M3`/`V2`/`D1` 各召回 0 条；查 `具体性与感官`/`视角一致性`/`意象复现` 各召回 5 条且全是作品技法条目 |

---

## 0. 一句话结论

**判据不走检索。**它由"维度 → 判据"的确定性映射直接注入 prompt，检索只继续负责"作品证据"。

理由一句话：判据是**判定标准**，标准的选择取决于你要判哪个维度，不取决于一段文本和标准的字面相似度。把它塞进字符匹配的检索引擎，等于用同一把尺子同时量两样东西。

## 1. 检索引擎事实（表格汇总：它不支持什么）

以下全部核过行号，不是推测。

| # | 事实 | 位置 | 后果 |
|---|---|---|---|
| F1 | 候选集只由 `knowledgeRecords` 生成，而它只拼「8 篇主库 + 12 篇补充库」共 20 条作品记录 | `src/lib/knowledge/catalog.ts:71` | **判据不在候选集里** → 检索 `S2` 恒为 0 分，不是排序输，根本没参赛 |
| F2 | 查询词 = NFKC 归一化后按非字母数字切词 + **每个汉字单字** + **每个相邻二元组** | `src/lib/ai/retrieval.ts:97-106` | 任何共享一个"的/与/是"的文本都得分 → 分数恒 > 0 → 永不空手而归 |
| F3 | 打分 = 命中项 × 字段权重，**无 IDF、无长度归一化、无阈值** | `retrieval.ts:108-110` | 高频词（视角、意象）不降权，5 个槽位必然填满，噪声与信号同权 |

| F5 | 分数是"字符命中 × 权重"的绝对和，query 越长分越高 | `retrieval.ts:108-110` | **分数不能跨查询比较**，不能拿来设相关性阈值或"是否够相关"的门禁 |
| F6 | `limit` 默认 5、硬上限 8；分析链路写死 `limit: 5` | `retrieval.ts:59-62`、`tasks.ts:242` | 槽位只够 5 条，第 6 条起召不回；想多给判据就得改调用点 |
| F7 | 管道强制 `chunkTypes = summary / technique_explanation / case_excerpt`，且 `allowImitation: false` | `src/app/api/ai/route.ts:135`、`retrieval.ts:40-41,73-77` | `text_sample`（原文片段级证据）**永远不出现**，证据粒度止步于"选段" |
| F8 | 索引是运行时代码拼的（`localCandidates` 现场构造），没有持久化索引 | `retrieval.ts:112-154` | **写进 JSON 不等于能被搜到**，新增条目必须改代码或在目录层扩展 |
| F9 | 输入超 `maxInputChars × 1.25` 直接回退 demo，不报错只给 warnings | `src/lib/ai/tasks.ts:273`、`route.ts:111`（默认 24,000） | 注入过量 = 静默降级成"离线演示结果"，用户只看到演示，不知道是撑爆的 |
| F10 | 输出 `max_tokens` 固定 5,000（`analysis-v2`） | `tasks.ts:285` | 已知基线缺陷：补了字段形状后 4/4 都 `finish_reason: length`，需 9,000+ |

### 1.1 由事实推出的三条硬约束

1. **不能靠"把判据写进知识库 JSON"让它被搜到**（F1 + F8）。这条路上限是 0，不是"效果不好"。
2. **不能给检索加"相关性阈值"来筛噪声**（F2 + F5）。分数不可比，加阈值只会把确定的好结果也筛掉。
3. **注入体积必须先算账再动手**（F9）。全量 18 条全文 = 29,453 字符，加 3,000 字原文就 32,453 > 30,000 门禁 → 必定 demo 回退。

## 2. 三种注入通道，裁决

| 通道 | 做法 | 裁决 | 理由 |
|---|---|---|---|
| **一：结构化注入**（推荐） | 代码里维护 `维度 → 判据 ID[]` 映射，按需把判据正文拼进上下文包 | **采用** | 判据选择由维度决定，确定性、可复现、可审计；不经过字符匹配，不受 F2–F5 影响 |
| 二：塞进 `knowledgeRecords` | 把判据当成第 21–38 条"作品" | **否决** | 污染作品库（`sourceStatus`/`author`/`plot` 字段全错位）；F2/F3 会把判据和作品混排；破坏"知识证据 = 作品证据"的隔离，让校验无法区分"引了作品"和"引了标准" |
| 三：向量库召回判据 | 建 pgvector 索引 | **本期不做** | PRD v2.0 已砍 pgvector 全量入库；且判据只有 18 条，精确匹配的检索质量上限本来就高于相似度匹配 |

## 3. 注入契约（给机器的硬规则）

### 3.1 注入对象（字段顺序即 prompt 里的顺序，不得重排）

```json
{
  "id": "S2",
  "维度": "结构组织",
  "判据": "（statement 原文，一字不改）",
  "可判定": "（checkable）",
  "量法": "（metric）",
  "正例": ["..."],
  "反例": ["..."],
  "易误报": ["..."],
  "不适用": "..."
}
```

### 3.2 裁掉什么

| 字段 | 进 prompt | 理由 |
|---|---|---|
| `authority` | ❌ | 出处是给人看的（答辩、审计），给模型只会诱导它复述文献名 |
| `note` | ❌ | 回代验证用的推导过程，进 prompt 等于把答案提前给出去 |
| `typicalTrue/False` | ✅ 只留各 1 条，不带 note | few-shot 一条足够定调；多给会把判据变成"模仿例句" |
| `commonFalsePositive` | ✅ 只留首条 | 误报面是判据的核心防线，但全列会挤爆预算 |
| `confidence` | ✅ 只给状态词 | `draft-pending-threshold` 必须原样出现，否则模型会把 pending 当二值判据用 |

### 3.3 数量与配额

- 单次请求 **最多注入 2 个维度、6 条判据**（实测 6 条 ≈ 3.1k–5.1k 字符，见 §6）
- 同一维度内注入其全部 3 条（六维各 3 条，成组注入，不拆）。**例外**：C1、D2 是 pending，日常诊断注入时跳过，该维度只剩 2 条（见 §3.6）
- 判据与作品证据的字符预算比建议 **不超过 1:1**（作品证据占 5 条，约 2k–3k 字符）
- **版本号不占预算**：prompt 里只出现 `[S2]`，`@v1.0` 由服务端事后附加（见 §3.5）

### 3.4 编号纪律

- 判据 ID 必须原样出现在 prompt 里，形如 `[S2]`
- 要求模型在输出里回填 `criteriaIds`，**不允许只写维度名**——维度名无法回溯判据版本，等于没有出处
- 模型只回填裸 ID（`S2`），**不带版本号**。版本由服务端在校验通过后附加（见 §3.5），prompt 一个字都不多加
- pending 条目（C1、D2）**日常诊断不注入**；只在离线采集模式下注入，且 ID 后附 `(pending)` 并明确要求只报数值、不下判断（见 §3.6）

### 3.5 版本溯源（已裁决：版本进输出，不进 prompt）

**问题**：库一升级，历史评测结果对不上——不知道当时判据是 v1.0 还是 v1.1。

**做法**：**版本不进 prompt，进了 prompt 也只会多一层噪音、多一份 token**。改为服务端附会：

```
模型输出        criteriaIds: ["S2", "P3"]
                 ↓ 校验（§5.2 三条）通过后
服务端写库/返给前端  criteriaIds: ["S2@v1.0", "P3@v1.0"]
```

**关键在于版本号从哪来**：不是模型给的，是 `criteria.ts` 装载判据时就知道的常量。所以：

| 环节 | 有没有版本 | 成本 |
|---|---|---|
| prompt 注入 | 无（只 `[S2]`） | **0 token** |
| 模型输出 | 无（只 `S2`） | 0 |
| 校验 | 无（按裸 ID 比对注入集合） | 0 |
| 结果落库 / 前端展示 / 评测记录 | 有（`S2@v1.0`） | 0 token，一次字符串拼接 |

**为什么这是安全的**：版本是**服务端事实**，不是模型的判断。让模型复述版本号只会给模型多一个编造的机会。模型该只回答"我按哪条判"，"那条当时是哪个版本"由系统记账。

**唯一要守的纪律**：`criteria.ts` 的版本常量必须与 `判据知识库_v1.0.md` 的文件名版本一致，改库时必须同步改常量。这条已写进维护手册 §3.2 的 B 型改动动作。

### 3.6 pending 条目（C1、D2）怎么处理（已裁决）

**裁决：日常诊断不注入；另走一条离线采集通道。**

悖论在这儿：C1、D2 的阈值依赖参照带，参照带要靠采集数值建起来，而"只采集不判定"的判据一旦不注入，就永远采不到数 → 阈值永远建不起来 → 永远 pending。

**三条出路，选最轻的**：

| 方案 | 成本 | 问题 |
|---|---|---|
| ① 直接注入日常诊断，要求模型只报数值 | 0 新增代码 | 模型看到"占比""差值"这类词就会自己下判断；而且 pending 判据会占掉本就紧张的 2 维度配额 |
| **② 复用现有 eval runner 离线采集**（**采用**） | **0 新增基础设施** | 无 |
| ③ 只对 C1、D2 所在维度临时开启注入 | 小 | 等于把 ① 的问题限制在两个维度里，没解决 |

**② 具体怎么做（不新建管道）**：

现有 `scripts/run-eval.mjs` 已经在做"跑一批样本、把结果写进 `evals/runs/*.json`"这件事。采集只是**多带两个字段**：

- 在 golden set 的输入里标记本次为采集运行（`collectOnly: true`），注入集合里加上 C1、D2
- prompt 侧对这两条只要求回填数值：C1 要 `K`（可说出关系的相邻句对数）、`P`（相邻句对总数）、可命名率；D2 要最高段密度、最低段密度、差值
- 结果里给 `criteriaIds: ["C1@v1.0", "D2@v1.0"]` 且 `verdict: "collect"`（不是 pass/fail）
- 校验层拦死：pending 条目若返回 `pass`/`fail`，按 `pending_verdict_forbidden` 丢弃该条

**累积到什么时候算够**：同一形态（叙述类 / 议论类分开）累积到 ≥ 30 个样本，取分位数划阈值，然后走维护手册 §3.2 的 **E 型改动**（pending → draft）。在那之前，**产品界面上一律不显示 C1、D2 的达标结论**，只显示"本条判据的阈值仍在标定中"。

**为什么不做成在线功能**：在线采集会让每个用户都在为别人的标定买单（多 2 条判据的 token + 可能被模型误判成结论）。标定是一次性工程动作，不该混进日常链路。

### 3.7 绝对不能注入的东西

- 六维的**定义长文**（§2 那 4,866 字符）：会诱导模型围绕定义套话，而不是围绕文本判定
- **§5 已知局限**：告诉模型"这条判据有误杀面"，它就会拿这个当豁免理由
- 任何"你是文学评论专家"式的角色铺垫：与现有 system prompt 冲突，且无实测收益

## 4. 检索接口规格（判据侧）

一期只做维度精确匹配，不读文本。**这一条是刻意的**：一旦让它读文本，就会退回 F2 的字符匹配。

```ts
type DimensionId = "结构组织" | "连贯衔接" | "信息密度与节奏"
                 | "具体性与感官" | "意象复现" | "视角一致性";

interface CriterionQuery {
  dimension: DimensionId;
  includePending?: boolean;   // 默认 false
  limit?: number;             // 默认 3，上限 3
}

interface CriterionHit {
  id: string;                 // S1/S2/S3/C1...
  dimension: DimensionId;
  block: string;              // §3.1 序列化后的正文
  status: "agreed" | "draft" | "draft-pending-threshold";
}

interface CriterionResult {
  mode: "exact" | "none";
  hits: CriterionHit[];
}
```

**返回 `mode: "none"` 时，面板必须显示"本次未匹配到判据"。**它与现有的"本次未召回知识条目"并列，是同一个诚实原则的两面：没给标准就不能出诊断，没给证据就不能出结论。

## 5. 输出与校验契约

### 5.1 新字段

```ts
interface LiteraryDiagnostic {   // 实际位置：src/lib/types.ts:74（不是 src/lib/ai/types.ts）
  // 现有字段不变
  dimension: DimensionId;     // 新增（该接口当前没有此字段）
  criteriaIds: string[];      // 新增：本次判定依据的判据 ID
  evidenceIds: string[];      // 现有：作品证据
}
```

`criteriaIds` 与 `evidenceIds` **平行且不混用**：前者是"我按哪条标准判的"，后者是"我引哪段原文为证"。

### 5.2 三条校验（加在 `src/lib/ai/validation.ts`）

| 校验 | 不通过时 | 为什么必须有 |
|---|---|---|
| `criteriaIds ⊆ 本次注入集合` | 丢弃，reason `unknown_criteria` | 防模型编判据 ID（比编引文更容易，因为 ID 短） |
| `criteriaIds` 非空 | 丢弃，reason `no_criteria` | **无标准的判断就是瞎说**。这是把"防幻觉"从"证据可核验"扩展到"判断有出处" |
| 同一处冲突只留一条（见 §5.2.1） | 丢后一条，reason `cross_dimension_conflict` | 防同一处被报两次、两边互相推 |

> **原第三条「维度前缀必须与 `dimension` 一致」已废**（2026-11-18 裁决）。理由见 §5.2.1：跨维度引用在真实文本里是常态，硬禁止会逼模型二选一，反而丢失信息。用一条通用冲突规则替代。

### 5.2.1 跨维度冲突：一条通用规则（已裁决）

**裁决原话：「冲突情况就都用通用的」**——不逐对列举，只定一条通用规则。

**第一步：什么算"冲突"**（必须有明确触发条件，否则规则形同虚设）

同一处文本位置同时满足以下两条，才算冲突：
- 两条诊断的 `quote` **指向同一段文字**（一个 `quote` 包含另一个，或两者有 ≥ 50% 字符重叠）
- 两条都判为**缺陷**（不是一条判缺陷、另一条判达标）

不同位置的缺陷、或一正一反的判定，**不算冲突，全部保留**。

**第二步：冲突了报哪条**

按「**判定所需人工解释量**」从少到多排一条链，只报最靠前的一条：

```
D（密度） > M（意象） > C（连贯） > V（视角） > S（结构） > P（具体性）
```

排序理由，一句话可讲清：**越靠左，判定越接近"数出来的"**。

| 维度 | 判定靠什么 | 需要多少解释 |
|---|---|---|
| D | 汉字数、事件数、词频 | 纯计数，几乎零解释 |
| M | 词频 + 段号 + 等同归组 | 归组有一点判断 |
| C | 指代词、连接词、主题词重叠 | 词表判定，边界清楚 |
| V | 人称、信息来源 | 要判"谁应该知道什么" |
| S | 段落功能归类 | "收束""推进"要靠语义归 |
| P | 抽象词 vs 具体名词 | 最依赖语义判断 |

**第三步：同维度内不适用这条链**，继续按《判据知识库》§4 的分工表（那里是「只报更具体的」，如 M1↔M2↔M3 报最具体的未过层）。**两条规则的分工说清楚**：维度内比"谁更具体"，维度间比"谁更硬"。

**为什么用硬度而不是"更重要"**：重要性是产品偏好，会随场景变，写进代码就变成拍脑袋；硬度是**可复算性的客观属性**，能一条链管住所有组合，不用维护 15 个维度对的例外表。这也正是「通用」的意思——**18 条判据任意两条撞上，都能用同一条链裁决**。

**落地位置**：校验层做（模型输出后仲裁），**不进 prompt**。理由：进 prompt 要模型自己比硬度，等于把确定性规则交给不确定的模型；校验层做是纯确定性代码，且 prompt 零增量。代价是模型可能多生成一条被丢的诊断（约 200 字输出），可接受。

### 5.2.2 `dimension` 字段怎么填

废掉前缀校验之后，`dimension` 只表示"这条诊断主要属于哪个维度"（前端分组用），**不再约束 `criteriaIds` 的前缀**。所以允许出现：

```json
{ "dimension": "结构组织", "criteriaIds": ["C2@v1.0"] }   // 用连贯的判据解释结构问题——合法
```

前端按 `dimension` 分组，但每条诊断下方展示的是它**实际依据的判据**（来自 `criteriaIds`）。两者不一致时以 `criteriaIds` 为准——那才是判断的真正来源。

### 5.3 与三态裁定的关系（注意：三态目前是设计态，不是实现态）

**目标态**（已写进 `docs/product-specs/literary-diagnosis-agent.md:43-47` 与 `docs/exec-plans/active/sprint-01-evidence-adjudication.md`，但**代码尚未实现**）：

| 情形 | 三态 |
|---|---|
| `evidenceIds` 不含任何 `knowledge` 证据 | `kept`，但标 `evidenceTier: "observation_only"` |
| 含 `knowledge` 证据 | `kept`，`evidenceTier: "anchored"` |
| 无 observation / user 证据 | `discarded`，附 `discardReason` |

**当前实现**（`src/lib/ai/validation.ts:330-340`，这是本节所有新校验的前置）：

诊断是**逐条**校验的，但失败语义是**整批**的——任何一条不合格 → `return null` → 整个 `analysis-v2` 输出作废。全库没有 `observation_only`、没有 `discardedDiagnostics`、没有 `discardReason`。（`docs/QUALITY.md:32` 写的「单条标记 `discarded` 并附 `discardReason`，其余诊断正常返回」是目标态，不是现状。）

**这直接决定本节的可行性**：§5.2 那三条校验全部写成「丢弃，reason `xxx`」——**单条丢弃的语义必须先于三条校验实现**，否则新校验只会让整批失败的触发率变高：模型少填一个 `criteriaIds`，用户端看到的不是"这条被丢了"，而是**整个诊断退化成 demo**。这会让"防幻觉"变成"防出结果"。

新增一层：`observation_only` 的诊断**仍必须有 `criteriaIds`**。也就是说纯观察型发现的底线是"我看得见这句话，我也说得出它违反了哪条标准"，不能只有前者。

## 6. 上下文预算（实测，不是估的）

测量脚本：`_inbox/measure_prompt_budget.py`（`字 = 汉字，不含标点`）。

| 方案 | 字符 | 汉字 | 粗估 tokens | 判定 |
|---|---|---|---|---|
| A 全量 18 条**全文** | 29,453 | 13,808 | 9.7k–13.8k | ❌ 加 3,000 字原文 = 32,453 > 30,000（F9 门禁）→ **必定回退 demo** |
| B 全量 18 条**prompt 版** | 12,758 | 8,829 | 6.2k–8.8k | ⚠️ 可行，但占 `maxInputChars`（24,000）的 53%，原文+证据只剩 11k |
| C **单维度 3 条** prompt 版 | 1,562–3,333 | — | 0.8k–2.3k | ✅ **推荐** |

单维度实测：具体性与感官 1,562｜意象复现 1,716｜结构组织 1,980｜连贯衔接 2,008｜视角一致性 2,159｜信息密度与节奏 3,333（D1/D3 的长例句是主因）。

### 6.1 结论

1. **"把 18 条全塞进去"在工程上是错误的**：不是成本问题，是**直接触发 demo 回退**，会让整个诊断功能静默失效。
2. 按维度分组注入（方案 C）时，判据只占 6–14% 的输入预算，与 5 条作品证据同量级，是可持续的。
3. **输出侧必须先修**：`analysis-v2` 的 5,000 tokens 在补字段形状后已经 4/4 截断（基线缺陷②），注入判据会让输出更长（多一个 `criteriaIds` 字段 + 更具体的建议）。**注入判据与调高 `max_tokens` 必须同批做**，否则会得到"判据注入了、输出被截断"的假失败。

## 7. 失败模式与观测点

| 症状 | 根因 | 观测点 |
|---|---|---|
| 模型输出的 `criteriaIds` 全空或全是维度名 | prompt 没要求回填，或 ID 标记被裁剪掉 | 校验计数 `no_criteria` |
| 每条诊断都引同一条判据 | 注入顺序固定 + few-shot 位置偏差 | 统计 `criteriaIds` 分布，单条占比 > 60% 即异常 |
| 结果整体变成 demo | 注入体积过门禁（F9） | `warnings` 里出现"作品上下文超过单次输入限制" |
| 说的标准与文本无关 | 注入了维度定义长文而非判据 | 抽查 prompt 快照 |
| 全知文本被判"视角不一致" | 注入了 V 类判据但没先判适用性 | 先跑 V1 的 `notApplicable`，命中即不注入 V2/V3 |
| 判据引了但证据没引 | 把 `criteriaIds` 当证据用了 | 校验层两者独立判定 |

## 9. 已裁决的四个问题（2026-11-18）

原来这四个是开放问题，现已全部拍板，这里留结论与指向，方便后续查。

| # | 问题 | 裁决 | 落在哪 |
|---|---|---|---|
| 1 | 判据版本要不要进输出？ | **进输出，不进 prompt**。模型只见 `[S2]`，服务端校验后拼成 `S2@v1.0`。prompt 零 token 增量 | §3.5 |
| 2 | 允不允许跨维度借判据？ | **允许**。废掉原来的前缀校验；冲突时按一条通用硬度链只报最靠前的一条 | §5.2.1 / §5.2.2 |
| 3 | pending 条目要不要注入？ | **日常不注入；复用现有 `scripts/run-eval.mjs` 离线采集**，不新建管道 | §3.6 |
| 4 | 要不要留 prompt 快照？ | **要，但只落在评测记录里**，不建表、不加接口 | §9.1 |

### 9.1 快照怎么留（轻量做法）

**不做的事**：不建 `prompt_snapshots` 表、不加查询接口、线上请求不留快照。

**做的事**：只借现有 `evals/runs/*.json` 的 `config` 段，加两个字段。现有结构长这样（`scripts/run-eval.mjs:299-306`）：

```json
"config": {
  "provider": "deepseek",
  "promptVersion": "taskInstructions@src/lib/ai/tasks.ts",
  "goldenSetVersion": "14 cases"
}
```

加两行就够：

```json
"config": {
  "criteriaVersion": "v1.0",
  "criteriaIdsInjected": ["S2", "S3", "C1"],
  "goldenSetVersion": "14 cases"
}
```

**为什么这样够用**：评测复现需要的是"当时注入的是哪几条、哪个版本"，而评测本来就要跑 `run-eval.mjs`，这一点信息是跑的时候现成的，写进已有的 run 文件里成本为零。线上请求不需要快照——线上结果是给人看的，评测结果才是要复现的。

**什么时候要升级成真快照**：出现"线上和评测结论对不上、需要回查线上当时注入了什么"这种争议时再说。目前没有这个需求，先不做。
