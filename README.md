# 故事熔炉 Story Forge

**一个「不相信 AI」的文学诊断工具。**

> 别人让 AI 帮你写。我想让它告诉你——这句话为什么不好，而且必须拿得出证据。

---

## 一、这个项目在解决什么

2026 年，让大模型点评一篇小说，任何人都能在十分钟内做出一个能跑的原型。

但真正用起来你会发现一个问题：**它会编。**

它会说"这里节奏拖沓"，但说不出哪一段拖沓。它会说"人物略显单薄"，但这句话换成另一篇小说同样成立。它会引用一句原文来"证明"自己的判断，而那句话在原文里根本不存在。

**这不是模型的错，是产品的错。**

因为大多数 AI 写作工具在设计时就没要求"结论必须可验证"——它们只要求"看起来专业"。

故事熔炉的出发点是一个反面命题：

> **每条诊断结论，要么能定位到原文的某几个字，要么就必须被丢掉。**
> 宁可少说，不许乱说。

这句话不是我事后总结的，是写进代码的硬约束：`analysis-v2` 的校验器会对每一条诊断检查三件事——引文是否逐字存在于用户原文、证据 ID 是否指向真实证据、结论是否引用了判据编号。**任何一条不满足，这条诊断被丢弃，而不是被降级显示。**

## 二、我是怎么发现"它在骗人"的

这个问题不是设计时想到的，是**跑出来的**。

我给文学诊断任务建了一套 14 条样本的评测集（golden set），第一次接真实模型跑，结果：

```
14 条样本，0 条通过校验，全部回退成演示数据。
```

也就是说——**这个功能从来没有真正工作过**。看到的全是假数据。

我花了七轮迭代才把它修通。每一轮的失败都不同，每一次失败都在教我一件事。

### 第一轮：模型不知道要返回什么形状

prompt 里列了字段名（`analysis`、`diagnostics`……），但从没说过这些字段**是什么形状**。

模型返回的 `analysis` 是个字符串，而代码期待数组。6 条样本里 5 条挂在这。

**教训**：给 LLM 的 prompt 里，"有哪些字段"和"每个字段长什么样"是两件不同的事。后者必须给结构示例。

### 第二轮：输出被截断了

补上形状说明后，4 条样本全部 `finish_reason: length`——输出预算 5000 tokens 不够。

**教训**：结构化输出的 token 消耗远超预期。改 prompt 和调预算必须同批做，否则会得到"改了 prompt 反而更差"的假象。

### 第三轮：校验器在逼模型编造缺陷

代码里有一条规则：叙事类文本的诊断中，**必须有一条提到"铺垫不足"**，否则整个结果作废。

这条规则是灾难性的。它把校验器变成了内容生成器——逼着模型必须造出一个"铺垫不足"的缺陷，哪怕文本里根本没有。

**教训**：校验器只能拒绝不合格的输出，绝不能规定输出必须包含什么。这两者差一个数量级。

### 第四到七轮：同一个病的七种表现

这一部分是我花时间最多、也最值得说的。

修好上面三个问题后，仍然 0/14。我开始逐轮排查，发现卡在"字段名对不上"：

| 模型返回的 | 代码要求的 |
|---|---|
| `evidence: {type, text}` | `{source, quote}` |
| `graph.nodes: {kind}` | `{type}` |
| `graph.edges: {from, to, relation}` | `{source, target, label}` |
| `styleProfile.metrics: {dimension: "句子长度"}` | `{key: "sentenceLength"}` |
| `paceCurve: {points: [{position, pace}]}` | `[{segment, value, evidenceId}]` |

**我一开始的做法是逐个补别名**——模型用 `type`，我就加 `type`；下次它用 `text`，我再加 `text`。

补到第七轮，我统计了一下：

> 同一个 `relationshipChanges` 字段，模型用过 **7 种写法**。
> 图节点类型允许 12 类，模型给过 **25 种**。

**补到第 10 个，它会想出第 11 个。这条路走不通。**

### 真正的解法：在入口做一次归一化

最后我建了一层 `normalize-payload.ts`，在校验前把模型的所有命名映射成 schema 要的形状。**改一个函数，通吃全部结构。**

结果：

| | 通过数 |
|---|---|
| 归一化前 | **0 / 14** |
| 归一化后 | **12 / 14** |

**这七轮里最值钱的一课不是技术，是判断**：当同一个问题以不同面目出现七次，说明我一直在治症状，没在治根因。识别出"这是同一个病"比修好它更难。

## 三、这个产品怎么定义"写得好"

（这一节是我的垂直优势——数字人文背景在这里变成了工程资产）

"文学诊断"最难的不是让 AI 说话，是**定义什么叫说得对**。

我的做法是建一套 **18 条判据的知识库**，六维 × 3 条：

| 维度 | 管什么 | 判据示例 |
|---|---|---|
| 具体性与感官 | 抽象判断有没有换成可指认的细节 | 有没有句子只堆抽象评价词而无具体名词 |
| 意象复现 | 反复出现的物件有没有承载含义 | 候选里有没有至少一个跨段复现 |
| 结构组织 | 段落功能和转折 | 最后一段有没有收束功能 |
| 连贯衔接 | 句与句的衔接 | 每个指代词都有明确先行词 |
| 信息密度与节奏 | 单位篇幅的新信息量 | 有没有连续 200 字不产生任何新信息 |
| 视角一致性 | 叙述者有没有越界 | 有没有"知道无人告知的信息" |

**每条判据都有 11 个字段**：可判定描述、计算规则、正例、反例、常见误报、不适用条件、置信状态……

其中两个字段最能说明这套东西的严谨程度：

- **`commonFalsePositive`（常见误报）**——同样长得像命中、但不该报的情形。例如"把概括性过渡句判成空转"。这是评测时区分"误报"和"真阳性"的依据。
- **`confidence`**——其中 `C1`、`D2` 两条标的是 `draft-pending-threshold`：**阈值依赖尚未建立的参照带，当前只采集数值、不产出达标结论。** 没有数据就不假装有结论。

### 我否决了什么（这部分比做成了什么更重要）

一套标准的价值，一半在于它收进了什么，另一半在于它**拒绝**了什么。

| 被否决的 | 理由 |
|---|---|
| **暗示与明写** | 属"文本意义表达方式"，与六维各自测的质量不是同一层 |
| **人物塑造（独立成维）** | 不满足"可量化"。成分拆入具体性、意象、结构三维 |
| **校对类意见**（措辞生硬、用词不当、标点） | 不是文学诊断 |
| **主题深度** | 需要读者立场与阐释框架，不可二值判定 |
| **反讽 / 幽默 / Voice** | 标注者之间一致性过低，或不可复算 |

**校对类那条有一个硬证据**：在评测基线阶段，模型通过校验后输出的内容退化为"育养一词稍显生硬""翻翻覆覆略显生硬"，而同一个模型在另一个样本上能输出"外貌降级的顶点，长衫换破夹袄"。

也就是说：**不是模型不会做文学诊断，是它一旦被允许谈措辞就只会谈措辞。**

这条证据说服我把校对意见挡在门外，并且在代码里加了拦截——用三层规则区分"针对一个词给替换建议"（校对）和"指出叙事处理的问题"（诊断）。

**代价我也认**：六维里从此没人直接管"人物"。被问到时的答案是——人物塑造是复合概念，已拆成可量化成分。这是取舍，不是疏漏。

## 四、砍掉了 90% 的功能

（这一节讲取舍判断）

这个项目一度有 27 个功能模块。现在真做的是 7 个。

砍的理由不是"做不完"，是**注意力只有 5–15 分钟**。一个什么都做了的项目，第一反应是"哪个都没做透"。

| 砍掉的 | 为什么 |
|---|---|
| 账号体系 + 手机验证 | 引入 Auth、数据迁移、注销清库，全是后端体力活，评委无感 |
| pgvector 向量库全量入库 | 18 条判据用精确匹配就够，上向量库是自造运维题 |
| 埋点自建表 + 数据闭环 | 企业赛要商业想象力，不要你真建好埋点表 |
| IP 实验场真实生图链路 | 非主线，降级为愿景叙事 |
| 主题热力图 / 直接分析跳转 | 与核心诊断重复，可视化统一收拢到可解释面板 |

**留下的是**：项目、人物、世界观、蓝图、正文、上下文一致性、文学诊断。

**判断标准只有一条**：这个选择会让作品里的"产品判断力"更清楚，还是更模糊？

## 五、现在的真实状态（不美化）

| 指标 | 数值 | 说明 |
|---|---|---|
| 诊断链路可用性 | **12 / 14** | 14 条评测样本中 12 条能返回真实诊断（曾长期为 0） |
| 证据可溯源率 | **100%** | 通过的结论全部可定位到原文 |
| 幻觉率 | **0%** | 无证据的结论在代码层被丢弃 |
| 诊断命中率 | **11 / 44** | 44 条预期发现中命中 11 条 |
| 判据知识库 | **18 条** | 六维 × 3，每条 11 字段 |
| 测试 | 58 个文件 / 347 个用例 | 含离线回放回归，`npm run verify` 全绿 |

**两个数字要分开看**：

- **12/14 是链路可用性**——说明"能出真结果"，不是说"判得准"。
- **11/44 是内容质量**——说明诊断还比较浅，这是下一步要攻的。

我不会把前者的好看数字当成后者的成绩。

## 六、下一步

按优先级：

1. **提高诊断命中率**（11/44 → 目标 25/44）：判据注入 prompt、扩充 golden set 到 30 条
2. **建立判据阈值**：`C1`、`D2` 目前只有采集、没有判定，需要积累参照带
3. **真实用户验证**：找 3–5 位数字人文同学实际使用，收集他们觉得"说得对/说得不对"的具体案例

第 3 项是当前最大的空白。**以上所有数字都是自评，没有一个真实用户的反馈。**

## 八、这个项目想证明什么

不是"我会写代码"——代码大部分是 AI 辅助写的。

我想证明的是三件更难的事：

1. **我能判断一个 AI 功能是真的能用，还是看起来能用**（12/14 vs 0/14 的区别）
2. **我能把一个主观领域的问题翻译成可计算的判据**（18 条判据、六维、11 字段）
3. **我知道什么该砍**（27 → 7，每一条都有理由）

这三件事，恰好是 AI 产品经理和"会调 API 的人"之间的差距。
